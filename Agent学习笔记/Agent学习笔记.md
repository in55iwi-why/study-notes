# 从 LLM 到 Agent Skill：完整学习笔记

---

## 一、概述：八个概念

| 概念 | 名词 | 一句话 |
| --- | --- | --- |
| 引擎 | LLM | 大脑，靠预测下一个 token 生成文本 |
| 数据 | Token | 模型眼里的最小文字单位 |
| 记忆 | Context | 此刻摆在桌上的全部信息 |
| 接口 | Prompt | 人把任务交给模型的方式 |
| 能力 | Tool / MCP | 手和插座，让模型能调用外部世界 |
| 框架 | Harness | 把发动机装成整车，负责组装上下文、调工具、控循环 |
| 决策 | Agent | 自主循环执行任务的系统 |
| 定制 | Agent Skill | 告诉 Agent 在这个领域具体怎么干活 |

---

## 二、LLM：一切的地基

### 2.1 它是什么

LLM 全称 Large Language Model，大语言模型，是整个体系最底层的引擎，它的底层架构是 Transformer。

- LLM 本身**只会续写文本**，不会主动做事
- 它不能自己获取实时信息，也不能自己执行操作
- 后面所有的 Tool、Agent、Skill，都是在外面包出来的能力。

---

## 三、Token

### 3.1 定义

Token 是大模型处理文本的**最小单位**，全称为Tokenizer（分词器），模型看的是 Token 和它对应的数字 ID。

### 3.2 编码与解码

- **编码分两步**：① 文本切分为 Token；② 每个 Token 映射为一个 Token ID（数字）
- **解码**：把 Token ID 还原为文本

---

## 四、Context 与 Context Window

### 4.1 定义

Context（上下文）是模型每次处理任务时接收的**信息总和**。它没有长期记忆——这一轮结束后，除非信息被放进下一轮输入，否则模型就"忘了"。

### 4.2 Context 的组成

- 用户当前的问题
- 对话历史
- 当前已经生成的输出 Token
- 工具列表（有哪些工具可用）
- System Prompt 等系统级指令
- 技能描述、检索到的资料片段

### 4.3 Context Window：记忆容量

### 4.4 RAG：突破窗口限制

RAG（检索增强生成）的思路是：从知识库里抽取与问题最相关的片段，**只把关键信息送进模型**。

### 4.5 上下文管理：Agent 的核心机制之一

上下文管理指的是：在有限的窗口里，决定**放什么、留什么、扔什么、什么时候去取**。具体包括：

- 保留相关历史，压缩或丢弃无关历史
- 从外部资料库检索相关片段补进来（RAG）
- 把工具调用结果放回上下文供模型继续推理
- 在技能命中时才加载完整指令（渐进式披露）

**它起到的作用**：让模型在正确的时间看到正确的信息。信息放多了浪费 token、干扰判断；放少了模型没依据，只能瞎猜。

---

## 五、Prompt：怎样描述任务才管用

### 5.1 定义与分类

Prompt 是给大模型的问题或指令，直接决定输出质量。分两类：

| 类型 | 定义 |
| --- | --- |
| User Prompt | 用户输入的具体任务 |
| System Prompt | 开发者后台配置的人设与做事规则 |

### 5.2 System Prompt 的性质

System Prompt 优先级通常高于 User Prompt，但它是**软约束**，不是代码级的安全边界，不能当成真正的权限控制来用。

---

## 六、Tool 与 MCP：能力层

### 6.1 Tool 是什么

Tool 是大模型可以调用的外部函数，让模型能够**感知和影响外部环境**。

它解决的痛点很直接：模型无法获取实时信息、计算能力有限、不能访问外部系统。

### 6.2 工具调用的完整流程

```text
用户提问
  ↓
平台转发（附带工具列表）给大模型
  ↓
大模型分析 → 生成工具调用指令（选哪个工具、参数是什么）
  ↓
平台执行调用 → 获取结果
  ↓
大模型整理结果 → 用自然语言输出给用户
```

### 6.3 工具调用机制起什么作用

它把 LLM 从"只能说话"变成了"能做事"：

- **感知**：读到文件、查到数据库、获取实时信息
- **行动**：写文件、执行命令、调用 API、修改外部系统
- **验证**：把结果拿回来让模型检查，形成闭环，而不是一次性输出

### 6.4 角色分工

| 角色 | 职责 |
| --- | --- |
| 大模型 | 选择工具、生成参数、归纳结果 |
| 工具 | 执行具体功能 |
| 平台 / Harness | 转发信息、执行工具调用、回灌结果 |

### 6.5 内置工具 vs 外置工具

- **内置工具**：某些 Agent 只有很少的内置工具。
- **外置工具**：可以自己写，也可以用别人做好的。

### 6.6 MCP 是什么

MCP 全称 **Model Context Protocol**（模型上下文协议），本质是**统一的工具接入标准**。

它解决的问题是：各平台各有各的接入规范，一个工具想接多个平台就得写多套。

把某个领域的全部工具交给一个 MCP 服务提供，Agent 只需要按统一协议调用。

### 6.7 MCP 与 Tool 的关系

- Tool 是能力本身
- MCP 是这种能力的接入标准

MCP 解决的是**连接问题**（怎么把外部工具和数据源接进来）。

---

## 七、Agent

### 7.1 它是什么

AI Agent 是能够**自主规划、自主调用工具、持续工作直到完成用户任务**的系统。核心能力包括多步骤推理、工具选择、流程控制。

### 7.2 Agent 与普通 LLM 对话的区别

这是理解 Agent 最关键的一张表：

| 对比维度 | 普通 LLM 对话 | AI Agent |
| --- | --- | --- |
| 交互方式 | 一问一答，你来我往 | 自主多轮循环，中途不需人盯着 |
| 能力边界 | 只生成文本 | 能调用工具改变外部世界（读写文件、执行命令） |
| 上下文 | 用户手动提供，模型被动接收 | 系统自动组装、检索、压缩和管理 |
| 任务粒度 | 单步任务 | 多步骤任务 |
| 规划能力 | 基本没有，走一步看一步 | 能拆解目标、安排步骤、调整计划 |
| 结束条件 | 回答完就结束 | 达成目标或触发终止条件才停 |
| 错误恢复 | 需要用户发现并纠正 | 可以观察工具结果，自己重试或换方案 |

### 7.3 一个 Agent 系统通常包含哪些部分

| 组成部分 | 作用 | 对应本文章节 |
| --- | --- | --- |
| LLM 模型 | 推理和生成的核心 | 第二章 |
| Prompt / System Prompt | 定义人设、能力和约束 | 第五章 |
| 上下文管理 | 决定给模型看什么，检索、压缩、回灌工具结果 | 第四章 |
| 工具层 | 感知和改变外部世界，含内置工具与 MCP | 第六章 |
| 任务规划 | 把大目标拆成可执行步骤，决定先做什么 | 本章 7.4 |
| Harness | 把以上所有部分串起来并驱动循环 | 第八章 |
| 记忆 | 短期上下文 + 长期记忆，保存跨会话的信息 | 第四章 |
| Skill 层 | 领域知识和流程，按需加载 | 第九章 |

### 7.4 三大机制分别起什么作用

- **工具调用**解决"**能不能做**"：给模型手和脚，让它能读写文件、查数据、执行操作。没有它，Agent 只是个会说话的大脑。
- **上下文管理**解决"**看什么**"：在有限的窗口里放对信息。没有它，模型要么没依据瞎猜，要么被无关信息淹没。
- **任务规划**解决"**先做什么**"：把模糊的大目标拆成有序的小步骤，并在执行中调整。没有它，模型面对复杂任务会东一榔头西一棒子。

### 7.5 核心是 loop

Agent 不是"问一次答一次"，而是循环工作：

```text
观察 → 思考 → 调用工具 → 看结果 → 再思考 → 再调用 → …… → 任务完成
```

它会一直循环，直到任务达成或触发终止条件。

### 7.6 两种典型构建模式

| 模式 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| ReAct | 每一步都"想一下再做一步"，推理和行动交替 | 灵活，能应对意外 | 步骤多，token 消耗大 |
| Plan and Execute | 先整体规划出步骤清单，再逐步执行 | 结构清晰，效率高 | 遇到意外情况需要重新规划 |

### 7.7 与 LLM 的关系

Agent 不是另一种模型，而是**包在 LLM 外面的控制系统**。LLM 负责每一步的推理和生成，Agent 负责决定什么时候停、调什么工具、下一步做什么。

## 八、Harness

### 8.1 什么是 Harness

在 Agent 系统里，**Harness 指围绕 LLM 的运行框架 / 脚手架**：它负责把模型、工具和执行流程串成一个真正能跑起来的系统。

### 8.2 Harness 具体做什么

| 职责 | 说明 |
| --- | --- |
| 上下文组装 | 接收用户输入，拼上系统提示、历史、工具列表、检索结果，形成最终送给模型的 Context |
| 模型调用 | 决定何时调用 LLM、传什么参数、要不要重试 |
| 输出解析 | 把模型输出解析成"普通回答"还是"工具调用指令" |
| 工具执行 | 真正去执行工具调用，拿到结果 |
| 结果回灌 | 把工具结果重新放进上下文，让模型继续推理 |
| 循环控制 | 管理多轮 loop，判断何时继续、何时终止、出错怎么处理 |
| 状态与记忆 | 维护会话状态、历史记录，必要时压缩或持久化 |
| 权限与边界 | 限制能访问哪些文件、能执行哪些命令，防止越界 |

### 8.3 它如何组织模型、工具和执行流程

**模型只负责"想"，Harness 负责"做"和"串"**。模型输出工具调用指令后，是 Harness 去执行、去回灌、去决定下一轮。

### 8.4 Harness 与 Agent 的关系

- **Agent** 是"能自主完成任务的系统"这个概念
- **Harness** 是让这个概念落地的工程实现

可以粗略地写成：**Agent = LLM + Harness（+ Tools / Skills）**。同一个 LLM，换一个 Harness，能力表现会完全不同——差别往往不在模型，而在 Harness 怎么组织上下文和工具。

## 九、Agent Skill

### 9.1 本质

Agent Skill 是一个可以被 Agent **按需加载的能力包 / 说明书**。它不是独立运行的程序，而是一份写清楚"某个领域该怎么干活"的文档，加上可选的配套资料和脚本。

### 9.2 三个组成部件

| 部件 | 作用 |
| --- | --- |
| `SKILL.md` | 主指令：什么时候用、怎么用、输出什么 |
| `references/` | 参考资料：领域知识、规范、案例 |
| `scripts/` | 可执行脚本：确定性的重复工作 |

### 9.3 另一种理解角度

补充一点差异：Claude Code 做了**上下文共享**，上一轮 Skill A 的历史在这一轮 Skill B 也能看到；而一般多智能体系统会刻意隔离上下文。

### 9.4 目录结构

推荐结构（正式规范）：

```text
my-skills/
└── meeting-summarizer/
    ├── SKILL.md              # 必需：元数据 + 主指令
    ├── references/
    │   ├── format-rules.md   # 可选：输出规范
    │   └── examples.md       # 可选：案例库
    └── scripts/
        └── extract_todo.py   # 可选：确定性脚本
```

命名规范：

- 使用小写英文 + 短横线
- 中文名称在 Claude Code 中实测兼容，但在 Claude Desktop 等严格环境下建议使用英文命名

### 9.5 高级用法一：Reference

把长篇的领域资料、规范文档、案例库放进 `references/`，不直接写进 `SKILL.md`。

**为什么**：全部塞进主指令会撑爆上下文，而且大部分资料在多数任务里根本用不上。

**怎么工作**：Agent 命中技能后先读 `SKILL.md`，正文里写明"需要时去读 `references/xxx.md`"，Agent 才会去读对应文件。

这和 RAG 的思想一致——按需取相关片段，只不过这里靠文件路径和指令控制，而不是靠向量检索。

### 9.6 高级用法二：Script

把确定性的、规则明确的工作写成脚本放进 `scripts/`，让 Agent 直接执行。

1. 代码比模型推理更稳：不会算错、格式跑偏、漏步骤
2. 更省 Token：脚本结果直接返回，不需要模型一步步推演
3. 一次写好，所有用到这个技能的任务都能复用

### 9.7 渐进式披露：Skill 最核心的设计

信息不是一次性全给，而是"需要多少给多少"。

| 层级 | 加载内容 | 时机 | 目的 |
| --- | --- | --- | --- |
| 第一层 | 技能的 `name` + `description` | 会话启动时常驻 | 让 Agent 知道有哪些技能可用，成本极低 |
| 第二层 | 完整的 `SKILL.md` | 用户请求与 description 匹配时 | 拿到这个任务的具体做法 |
| 第三层 | `references/` 文档、`scripts/` 执行 | 主指令明确要求时 | 补充资料或执行确定性动作 |

**带来的好处**：

1. **省 Token / 省上下文窗口**：装 50 个技能，平时只占 50 段 description 的空间
2. **技能之间不打架**：不相关的指令不会同时进入上下文互相干扰
3. **可以做得很大**：一个 Skill 背后可以挂几十个 reference 文件和脚本，不拖慢日常工作

**一句话区分**：MCP 提供"能用什么"（连接标准），Skill 提供"该怎么做"（流程指令）。

| 对比维度 | Agent Skill | MCP |
| --- | --- | --- |
| 本质 | 一份 Markdown 说明书 + 配套资源 | 一种工具接入协议 |
| 解决问题 | 任务流程、领域知识、输出规范 | 外部工具和数据源怎么连进来 |
| 存在形式 | 本地文件夹（`SKILL.md` 等） | 服务端 / 客户端协议实现 |
| 加载方式 | 按需进入上下文（渐进式披露） | 工具列表常驻，调用时才执行 |
| 谁来写 | 领域专家、普通用户也能写 | 通常是开发者 / 工具提供方 |

## 十、写一个 Skill

1. 在 `.claude/skills/` 下新建一个文件夹。
2. 在文件夹里新建 `SKILL.md`。
3. 文件最顶部写 YAML 元数据：`name` 用小写英文加短横线，`description` 写清楚"什么情况下用我"。
4. 正文按"目标 / 执行步骤 / 输出格式 / 示例"四段写，越具体越好。
5. 如果有长资料，新建 `references/` 文件夹放进去，并在正文里写明什么时候读哪个文件。
6. 如果有固定动作，写成脚本放 `scripts/`，在正文里写明调用方式。
7. 测试：用一句符合 description 的话提问，看 Agent 有没有激活这个技能；再故意问一个不相关的问题，确认它不会被误激活。

## 十一、Skill 与 MCP

### 11.1 什么时候用 Skill

Skill 适合**流程固定、规范明确、需要反复执行**的任务，尤其是"你知道该怎么做，但每次都要重新交代一遍"的场景。

| 开发任务 | Skill 里写什么 |
| --- | --- |
| 代码审查 | 团队的命名规范、必查项、输出格式 |
| 项目脚手架 | 新项目的目录结构、必需文件、配置文件模板 |
| 会议纪要 / 周报 | 提取规则、输出模板、待办格式 |
| 文档生成 | 接口文档的结构、示例写法、术语表 |
| 特定框架的代码生成 | 团队惯用的写法、组件结构、禁止用法 |
| 数据分析流程 | 清洗步骤、统计口径、图表规范 |

### 11.2 什么时候用 MCP

MCP 适合**需要连接外部系统或数据源**的任务，尤其是"模型本身拿不到这些信息"的场景。

| 开发任务 | MCP 提供什么 |
| --- | --- |
| 查数据库 | 连接 PostgreSQL / MySQL，执行查询并返回结果 |
| 代码托管平台操作 | 连接 GitHub / GitLab，创建 issue、查 PR、看 CI 状态 |
| 设计稿转代码 | 连接 Figma，读取设计稿结构和标注 |
| 内部 API 调用 | 连接公司内部的工单系统、知识库、监控平台 |
| 文件系统 / 浏览器 | 读写本地文件、打开网页、抓取页面内容 |
| 实时信息 | 查天气、查股价、查文档站点的最新版本 |

## 十二、六个核心问题速答

### 12.1 问题 1：什么是 AI Agent？它与普通的大语言模型对话有什么区别？

AI Agent 是能**自主规划、自主调用工具、持续工作直到完成任务**的系统。普通 LLM 对话是"一问一答、只生成文本、上下文靠人手动给"；Agent 是"多轮自主循环、能调用工具改变外部世界、自动管理上下文、能拆解任务并自我纠错"。一句话：**LLM 是回答问题，Agent 是完成任务**。

### 12.2 问题 2：除了底层 LLM，一个 Agent 系统通常还包含哪些部分？工具调用、上下文管理、任务规划分别起什么作用？

还包含：Prompt / System Prompt、上下文管理、工具层（含 MCP）、任务规划、Harness、记忆、Skill 层。

- **工具调用**解决"能不能做"：给模型手和脚
- **上下文管理**解决"看什么"：在有限窗口里放对信息
- **任务规划**解决"先做什么"：把大目标拆成有序步骤

### 12.3 问题 3：什么是 Harness？它如何组织模型、工具和执行流程？

Harness 是围绕 LLM 的**运行框架 / 脚手架**，本义是"马具"。它负责组装上下文、调用模型、解析输出、执行工具、回灌结果、控制循环、管理状态和权限。组织流程是：用户任务 → Harness 组装 Context → 调 LLM → 解析出工具指令 → 执行工具 → 结果回灌 Context → 再调 LLM → 直到任务完成。可以粗略写成 **Agent = LLM + Harness（+ Tools / Skills）**。

### 12.4 问题 4：我们应该怎样描述任务、提供上下文，才能让 AI 更准确地完成工作？

用六要素模板：**角色 + 背景 + 目标 + 约束 + 输出格式 + 示例**。另外注意：给材料而不只给要求、说清完成标准、复杂任务先让它复述理解、大任务拆小步、迭代时指出具体问题、要求给出依据。

### 12.5 问题 5：AI Agent 能否成为我们的"外置大脑"，融入日常学习、资料整理和项目开发？

能，但定位是"替你承担信息搬运和初步加工"，不是替你思考。学习上可以当教练（讲解、提示、追问、错题归纳）；资料整理上可以提炼、归类、转换、对比；项目开发上可以做需求分析、代码解释、调试、集成、测试、文档。边界是：事实要核对、隐私要注意、代码要运行验证、别让它替你思考、长期信息要写下来。

### 12.6 问题 6：什么是 Agent Skill 和 MCP？分别可以在怎样的开发任务中使用？

**Skill** 是按需加载的领域任务说明书（`SKILL.md` + `references/` + `scripts/`），适合流程固定、规范明确、反复执行的任务。**MCP** 是统一的工具接入协议，适合需要连接外部系统和数据源的任务。两者不是二选一：**MCP 解决"连得上"，Skill 解决"用得对"**。
